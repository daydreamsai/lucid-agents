# MPP and x402 release and gap analysis

**Research date:** 24 July 2026  
**Repository baseline:** current workspace against `origin/master`  
**Scope:** The latest released MPP/`mppx` and x402 TypeScript capabilities, compared with `packages/mpp` and `packages/payments`.  
**Method:** Primary sources only: protocol specifications, official documentation, official repositories and changelogs, release tags, published package metadata, and the pre-implementation repository source. This report records the baseline that informed the implementation in this branch.

## Executive conclusion

Lucid has a strong application-level payment boundary: one protocol-neutral HTTP authorization gate coordinates payment verification, idempotency, policy reservation, business execution, settlement, and durable accounting for invoke, stream, and task admission. That is a more valuable foundation than another framework-specific `402` middleware.

The protocol integrations behind that boundary are now materially stale:

- The lockfile mixes `@x402/core` **2.18.0** with `@x402/evm`, `@x402/fetch`, and `@x402/svm` **2.2.0**, including nested `@x402/core` 2.2.0 copies. The current coordinated x402 TypeScript release is **2.19.0**, published 17 July 2026. This is a P0 compatibility and security-baseline problem, not merely a missing-feature problem.
- The lockfile resolves `mppx` **0.4.12**, while Lucid's README says 0.4.11 and the current upstream release is **0.8.13**, published 22 July 2026. Since 0.4.x, `mppx` has added production session persistence and recovery, TIP-1034 sessions, subscriptions, EVM charges, x402 compatibility, multi-offer discovery, payment preferences, and MCP payment transports.
- Lucid's custom SIWX wire shape and request-derived domain have diverged from x402 2.19, which requires the official `sign-in-with-x` extension and an operator-configured public origin. This is a P0 interoperability and trust-boundary gap.
- Lucid's x402 integration supports one fixed-price `exact` offer on one configured EVM or Solana network. It does not expose current x402 `upto`, `batch-settlement`, multiple accepted offers, token-denominated offers, the official extension system, most current networks, or paid MCP transport.
- Lucid's MPP integration correctly emits Payment-Auth challenges and can natively verify Tempo and Stripe charges, but native Tempo sessions are deliberately disabled, `subscription` is absent from the type model, challenge state is process-local, discovery is Agent-Card-specific rather than MPP OpenAPI discovery, and HTTP is the only payment transport.

The recommended sequence is:

1. **Now:** align and pin coherent dependency sets, adopt current SIWX origin/wire semantics, add upstream-version/conformance CI, harden the current MPP wire contract, migrate MPP challenge state behind a durable atomic store, and publish an exact support matrix.
2. **Next:** make x402 offers/schemes/extensions a registry owned by `@lucid-agents/payments`; add `upto`, then batch settlement; migrate `@lucid-agents/mpp` to current sessions, multi-method discovery, and EVM charge.
3. **Later:** add a protocol-neutral MCP adapter, MPP subscriptions, broader optional network mechanisms, and advanced attribution/receipt/observability features.

## What the current protocols can do

### x402 2.19.0

The official TypeScript SDK's current surface is much broader than fixed EVM USDC:

- **Schemes:** `exact` fixed-price payments; EVM Permit2 `upto` payments where the buyer authorizes a ceiling and the seller settles actual usage; and EVM `batch-settlement`, where a funded channel signs off-chain vouchers and redeems them onchain in batches. Sources: [scheme overview](https://docs.x402.org/schemes/overview), [`upto`](https://docs.x402.org/schemes/upto), [batch settlement](https://docs.x402.org/schemes/batch-settlement).
- **Assets and networks:** any EVM ERC-20 through EIP-3009 or Permit2, any Solana SPL/Token-2022 token, plus released TypeScript exact implementations for TON, Algorand, Stellar, Aptos, Hedera, Keeta, NEAR, Concordium, and XRPL. A custom atomic `TokenAmount` works where a dollar-string default asset does not. Sources: [network and token support](https://docs.x402.org/core-concepts/network-and-token-support), [SDK feature matrix](https://docs.x402.org/sdk-features).
- **Multiple offers:** a route can expose an `accepts` array spanning schemes, networks, assets, and destinations; clients register compatible schemes and select an offer. Source: [seller quickstart](https://docs.x402.org/getting-started/quickstart-for-sellers).
- **Extensions:** Bazaar endpoint/MCP discovery, payment identifiers for reconciliation and idempotency, SIWX, signed offers and receipts, EIP-2612 and generic ERC-20 approval gas sponsorship, and ERC-8021 builder-code attribution. Source: [extension overview](https://docs.x402.org/extensions/overview).
- **Lifecycle and recovery:** client, resource-server, facilitator, scheme, and extension hooks cover creation, verification, settlement, failures, cancellation, and protected-request execution. 2.19.0 specifically allows a later post-verification hook to abort and trigger cleanup of state reserved by an earlier scheme hook. Sources: [lifecycle hooks](https://docs.x402.org/advanced-concepts/lifecycle-hooks), [2.19 core changelog](https://github.com/x402-foundation/x402/blob/main/typescript/packages/core/CHANGELOG.md#2190).
- **Transports and integration:** HTTP framework middleware and Fetch/Axios clients are released; MCP server wrappers and auto-paying clients are first-class and Bazaar can index MCP tools. Source: [SDK feature matrix](https://docs.x402.org/sdk-features).
- **Wallet compatibility:** released EVM mechanisms cover EOAs, deployed smart accounts, ERC-6492 counterfactual wallets under facilitator allowlists, and ERC-7702-delegated EOAs, with scheme-specific limits. Source: [wallet compatibility](https://docs.x402.org/advanced-concepts/wallet-compatibility).

The latest release is also a security signal. The 2.19.0 EVM changelog fixes unauthenticated path traversal and pre-verification state mutation in batch-settlement file storage, while the extension release requires SIWX to bind challenges and proof validation to an operator-configured public origin. Lucid does not currently enable batch settlement, but the fix demonstrates why mixed old mechanism packages are unsafe as a future baseline. Sources: [2.19 EVM changelog](https://github.com/x402-foundation/x402/blob/main/typescript/packages/mechanisms/evm/CHANGELOG.md#2190), [2.19 extensions changelog](https://github.com/x402-foundation/x402/blob/main/typescript/packages/extensions/CHANGELOG.md#2190).

### MPP and `mppx` 0.8.13

The underlying Payment Authentication draft remains deliberately method- and intent-agnostic. MPP's current reference SDK has moved well beyond one charge per HTTP request:

- **Charges:** Tempo stablecoin, Stripe Shared Payment Token, and EVM charge methods; EVM charge can answer standard Payment-Auth and compatible x402 `exact` clients on arbitrary EVM networks. Sources: [MPP EVM/x402 announcement, 8 Jun 2026](https://mpp.dev/blog/evm-x402-support), [`mppx` changelog](https://github.com/wevm/mppx/blob/main/CHANGELOG.md#0629).
- **Sessions:** a client opens a funded channel, sends cumulative vouchers as usage grows, tops up, then closes and recovers unused funds. TIP-1034 sessions became the default interface in 0.7.0 on 11 June; current support includes HTTP, SSE, and WebSocket metering, persistent channel stores, server snapshots, safe client rehydration, and settlement hooks. Sources: [improved sessions announcement, 17 Jun 2026](https://mpp.dev/blog/sessions-improved), [0.7.0 release](https://github.com/wevm/mppx/releases/tag/mppx%400.7.0), [0.8.13 release](https://github.com/wevm/mppx/releases/tag/mppx%400.8.13).
- **Subscriptions:** Tempo subscriptions authorize recurring access once, persist a merchant-scoped subscription record, reuse access within a paid period, and support request-path or scheduled renewal. Source: [subscriptions announcement, 12 May 2026](https://mpp.dev/blog/subscriptions).
- **Negotiation and discovery:** `Accept-Payment` preferences let clients filter/order offers, while canonical OpenAPI `x-payment-info.offers[]` can declare several methods, currencies, and intents for one route without probing it first. Sources: [`mppx` 0.5.12 changelog](https://github.com/wevm/mppx/blob/main/CHANGELOG.md#0512), [multi-method discovery announcement, 28 Apr 2026](https://mpp.dev/blog/multi-method-discovery).
- **MCP/JSON-RPC transport:** the Payment Authentication MCP draft maps challenges to JSON-RPC error `-32042`, credentials to request metadata, and receipts to result metadata; `mppx` 0.8 wraps MCP SDK clients and handles payment-required errors or tool results. Sources: [Payment Authentication MCP transport draft](https://paymentauth.org/draft-payment-transport-mcp-00), [`mppx` 0.8.0 release](https://github.com/wevm/mppx/releases/tag/mppx%400.8.0).
- **Production state and hooks:** upstream added atomic custom-store updates for distributed replay/channel safety, typed client/server payment events, validation APIs/CLI, and persistent session stores. Sources: [`mppx` 0.5.8 changelog](https://github.com/wevm/mppx/blob/main/CHANGELOG.md#058), [`mppx` 0.6.21 changelog](https://github.com/wevm/mppx/blob/main/CHANGELOG.md#0621), [0.8.13 release](https://github.com/wevm/mppx/releases/tag/mppx%400.8.13).

MPP is still a work in progress, not an RFC. The current core, discovery, MCP transport, and Tempo session drafts were published on 17 July 2026. Lucid's README still names the superseded `draft-ryan-httpauth-payment-01`. Lucid should name the exact draft and SDK compatibility set in its support matrix instead of treating “MPP support” as a timeless binary. Sources: [current core draft](https://paymentauth.org/draft-httpauth-payment-00), [discovery draft](https://paymentauth.org/draft-payment-discovery-00), [MCP transport draft](https://paymentauth.org/draft-payment-transport-mcp-00), [official spec index](https://paymentauth.org/).

The maturity labels matter. The official sessions announcement calls `session` a formal cross-network intent, but the generic intent draft is not published in the official spec index as of the research cutoff; method-specific session drafts exist. Tempo subscriptions are implemented by `mppx` and officially announced, but no subscription-intent draft appears in the current public spec tree. Treat both as SDK capabilities, and subscriptions especially as experimental interoperability, rather than finalized standards. Sources: [sessions announcement](https://mpp.dev/blog/sessions-improved), [subscriptions announcement](https://mpp.dev/blog/subscriptions), [official specification tree](https://github.com/tempoxyz/mpp-specs/tree/main/specs).

## Lucid's current implementation

### Strengths worth preserving

1. **A real application transaction boundary.** The HTTP package delegates all adapters and task transports through one authorization gate. It resolves one rail, verifies SIWX/MPP/x402, derives a stable payer subject, admits policy capacity, and exposes `abort`, `finalize`, and post-commit recovery around execution. Evidence: [`packages/http/src/authorization.ts:98-109`](../../packages/http/src/authorization.ts#L98-L109), [`:147-167`](../../packages/http/src/authorization.ts#L147-L167), [`:191-233`](../../packages/http/src/authorization.ts#L191-L233), [`:265-297`](../../packages/http/src/authorization.ts#L265-L297).
2. **Durable policy accounting.** Incoming and outgoing policy reservations can be durably staged before irreversible settlement and committed afterward, preventing reservation expiry from reopening spend after settlement. Evidence: [`packages/types/src/payments/index.ts:96-170`](../../packages/types/src/payments/index.ts#L96-L170), [`packages/payments/src/incoming.ts:314-613`](../../packages/payments/src/incoming.ts#L314-L613).
3. **Correct x402 v2 HTTP shape.** Incoming requests use the current v2 headers, official resource-server/facilitator abstractions, and delayed settlement after successful application work. Evidence: [`packages/payments/src/incoming.ts:824-875`](../../packages/payments/src/incoming.ts#L824-L875).
4. **Standard Payment-Auth wire format.** MPP emits `402` with Problem Details and `WWW-Authenticate: Payment`, decodes `Authorization: Payment`, and attaches `Payment-Receipt`; challenge IDs are target-bound and fenced against concurrent replay. Evidence: [`packages/mpp/src/challenge.ts:136-190`](../../packages/mpp/src/challenge.ts#L136-L190), [`packages/mpp/src/middleware.ts:14-50`](../../packages/mpp/src/middleware.ts#L14-L50), [`packages/mpp/src/extension.ts:254-335`](../../packages/mpp/src/extension.ts#L254-L335).
5. **Useful protocol pluralism.** Entrypoints can select x402 or MPP, and verified MPP payments reuse the same incoming policy/accounting path as x402. Evidence: [`packages/http/src/authorization.ts:147-167`](../../packages/http/src/authorization.ts#L147-L167), [`:217-233`](../../packages/http/src/authorization.ts#L217-L233).

These assets should remain above protocol-specific SDKs. The upgrade should replace protocol mechanics, not push payment logic back into Hono, Express, Next, or TanStack adapters.

## Detailed design recommendations

### 1. Fix version coherence before adding features

The highest-risk local fact is not that Lucid lacks `upto`; it is that objects from `@x402/core` 2.18 are being composed with scheme/client classes built against nested core 2.2. A successful TypeScript build does not establish wire or lifecycle compatibility across that split. The 2.19 core lifecycle contract also has cleanup behavior that a 2.2 mechanism cannot know about.

The upgrade should:

1. Pin `@x402/core`, `@x402/fetch`, `@x402/evm`, `@x402/svm`, and any new `@x402/extensions` dependency to the same tested release family.
2. Add a lockfile assertion that there is one expected `@x402/core` version beneath all direct x402 packages.
3. Exercise official-style EVM exact and SVM exact client/server/facilitator fixtures, including duplicate settlement, malformed payloads, settlement failure, request-body retry, and SIWX origin tests.
4. Upgrade `mppx` in a separate compatibility branch. Its 0.5–0.8 releases contain intentional breaking surface changes, notably MCP and session APIs.
5. Pin the exact protocol and SDK versions in public docs and expose a generated feature matrix.

Add an immediate regression test for paid `fetch(new Request(...))` POST retries preserving the request body. Upstream fixed this after 2.19.0, so the test should run against Lucid's chosen patch/backport and then the next coordinated x402 release; the post-release commit itself must not be described as 2.19 functionality. Source: [upstream body-preservation fix](https://github.com/x402-foundation/x402/commit/27fadeb3).

### 2. Model offers, not another pile of flags

Adding `upto?: true`, `batch?: true`, `asset?: string`, and several extension booleans to `PaymentsConfig` would create the same single-offer limitation under more flags. The durable abstraction is a list of protocol-owned offers:

```ts
type X402Offer =
  | {
      scheme: 'exact';
      network: Network;
      price: Money | TokenAmount;
      payTo: string | DynamicPayTo;
      extensions?: X402ExtensionDeclaration[];
    }
  | {
      scheme: 'upto';
      network: `eip155:${string}`;
      maximum: Money | TokenAmount;
      settle: X402UsageSettlement;
      payTo: string;
      extensions?: X402ExtensionDeclaration[];
    }
  | {
      scheme: 'batch-settlement';
      network: `eip155:${string}`;
      maximum: Money | TokenAmount;
      channelStore: X402ChannelStore;
      payTo: string;
      extensions?: X402ExtensionDeclaration[];
    };
```

This is illustrative, not a proposed public API commitment. The current `price: '0.01'` should remain sugar that compiles to one exact offer. `@lucid-agents/payments` should materialize complete x402 servers and clients from the offer set and expose them directly to the HTTP/MCP transport layers.

For `upto`, Lucid's application boundary provides a differentiator: reserve policy capacity against the advertised ceiling before handler execution, derive actual usage from a typed handler result or settlement callback, reject values above the ceiling, settle, then commit actual accounting and release the difference. That belongs in the payments runtime, not each adapter.

### 3. Make MPP state durable before claiming production sessions

Lucid's existing MPP map correctly fences same-process concurrent replay, but it cannot protect a multi-replica service. A store port should own:

- challenge creation with expiry and target/body binding;
- atomic `issued → verifying → verified/consumed` transitions;
- idempotency-key-bound receipt recovery;
- replay rejection after restart;
- session channel/subscription records as separate domain records;
- cleanup without weakening permanent replay evidence needed by a rail.

Use isolated in-memory storage as the portable default, with explicit SQLite/Postgres factories following the payments package's existing storage pattern. Current `mppx` atomic `Store.update()` and session `ChannelStore` interfaces should inform adapters, but Lucid should not leak an upstream store type into core or HTTP.

The same migration should close the July draft's wire gaps: include and verify an RFC 9530 request-body `digest` for body-bearing operations; reject production Payment challenges/credentials on plaintext HTTP; use current Problem Details failure types; and decorate any response carrying `Payment-Receipt` with `Cache-Control: private`. The current implementation already sends `no-store` on 402 challenges, so this is an extension of an existing correct boundary rather than a new subsystem. Source: [current Payment Authentication core draft](https://paymentauth.org/draft-httpauth-payment-00).

### 4. Adopt official extensions where they overlap current Lucid features

Lucid's custom SIWX implementation predates the current official package and now risks semantic drift, particularly around 2.19's configured-origin requirement and structured failure codes. Migration should preserve Lucid's durable nonce/entitlement storage through an adapter to the official extension lifecycle.

Recommended extension order:

1. **Payment identifier:** connect it to Lucid invocation idempotency and reconciliation without treating the identifier alone as authority.
2. **Bazaar:** generate endpoint and, later, MCP discovery from the canonical entrypoint definition.
3. **SIWX:** migrate wire/lifecycle behavior to upstream while retaining Lucid storage and handler auth context.
4. **Signed offers/receipts:** surface verifiable commercial artifacts in task and analytics records.
5. **Builder code:** optional attribution for ecosystem distribution.
6. **Gas sponsorship:** optional server declarations and client capabilities, enabled only where the facilitator and signer support them.

### 5. Keep transport and protocol ownership clean

The existing architecture principle is correct and should govern the work:

| Package                    | Owns                                                                                                                                                 | Must not own                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `@lucid-agents/types`      | Canonical cross-package contracts for payment offers, settlement results, stores, and transport-neutral capabilities                                 | x402 or MPP implementation logic                                  |
| `@lucid-agents/payments`   | x402 schemes, mechanism/extension registration, facilitator communication, SIWX integration, policy reservation, settlement, reconciliation          | Hono/Express/Next route-specific paywalls                         |
| `@lucid-agents/mpp`        | Payment-Auth methods/intents, challenge and credential verification, durable challenge/session/subscription state, receipts, MPP client construction | x402's official configuration or generic application routing      |
| `@lucid-agents/http`       | Map HTTP requests/responses to complete runtime capabilities and preserve the canonical application transaction                                      | Scheme selection, facilitator verification, duplicated registries |
| Future `@lucid-agents/mcp` | Map MCP/JSON-RPC payment metadata and tool calls to the same entrypoints and runtime capabilities                                                    | Payment-method verification or independent business handlers      |
| `@lucid-agents/core`       | Extension composition and one entrypoint registry                                                                                                    | Payment-method branches or protocol SDK types                     |

MPP's `mppx` can understand compatible x402 challenges, which is useful for outbound negotiation. It should not create a second server-side x402 configuration source inside `@lucid-agents/mpp`; official x402 selling remains owned by `@lucid-agents/payments`.

## Now / Next / Later roadmap

### Now — compatibility and production safety

1. **Coherently upgrade x402 to 2.19.x** and assert one version family in the lockfile.
2. **Migrate SIWX to the 2.19 trust boundary** with required public `origin`, official extension shape/result codes, and Lucid storage adapters.
3. **Open a controlled `mppx` 0.8 migration** with compile/API review from 0.4.12 through 0.8.13; do not change the public MPP claim until protocol fixtures pass.
4. **Bring MPP HTTP conformance current:** multi-challenge/`Accept-Payment`, canonical OpenAPI offers, body digest, private receipt caching, TLS guard, and current failure semantics.
5. **Add conformance suites** for x402 exact EVM/SVM and MPP Tempo/Stripe charge, including POST-body retry, replay, concurrency, wrong-origin/target/body, settlement failure, and restart cases.
6. **Add a durable MPP challenge-store port** and production SQLite/Postgres implementations.
7. **Correct documentation drift** (superseded MPP draft and `mppx` 0.4.11 vs 0.4.12) and publish a generated support matrix distinguishing protocol, SDK, transport, network, intent, and storage support.

**Exit criterion:** no mixed x402 core/mechanism versions; SIWX cannot be redirected by Host/forwarded headers; exact EVM/SVM and MPP charge fixtures pass against pinned upstream releases; MPP negotiation/discovery matches the July drafts; MPP replay survives multi-replica/restart testing; docs name exact versions and known exclusions.

### Next — close the high-value commercial gaps

1. **Introduce domain-owned x402 offers and registries** while preserving `price` sugar.
2. **Ship `upto` end to end** with typed usage settlement and ceiling-vs-actual policy accounting.
3. **Register payment-identifier, Bazaar, and official SIWX**; then signed offers/receipts.
4. **Ship batch settlement** with explicit Redis/Postgres-style durable channel storage and reconciliation.
5. **Add current native MPP EVM charge and Tempo sessions**, including session account, store, HTTP/SSE metering, top-up/close, snapshots, and settlement hooks.
6. **Generate canonical MPP OpenAPI multi-offer discovery** and honor client payment preferences.

**Exit criterion:** one entrypoint can advertise several x402 offers, charge actual usage safely, be discovered through Bazaar and MPP OpenAPI metadata, and run a restart-safe MPP session without custom verification code.

### Later — distribution and broader rails

1. **Add `@lucid-agents/mcp`** so the same typed entrypoint is a paid MCP tool over x402 or MPP without a second handler.
2. **Add MPP subscriptions** with durable records, idempotent renewal, scheduler integration, and operational controls.
3. **Add optional network mechanism packages** based on facilitator and customer demand rather than expanding one hard-coded allowlist.
4. **Expose bounded payment lifecycle events** for analytics, reconciliation, incident response, and signed receipt retention.
5. **Add builder-code and supported gas-sponsoring extensions**, plus UI/CLI controls.
6. **Monitor, do not prematurely claim, post-2.19 work** such as SVM `upto` and server-supplied recent blockhash until it is released and facilitator support is available.

**Exit criterion:** HTTP, tasks, streams, and MCP share one paid capability contract; recurring/session commerce is observable and restart-safe; optional rails do not inflate portable runtimes.

## Validation plan for implementation tickets

Every protocol addition should be accepted only with:

- an upstream-version fixture or official example translated into a Lucid smoke test;
- seller and buyer tests, not server-only unit tests;
- malformed, replayed, concurrently submitted, wrong-origin, wrong-target, and expired credential cases;
- facilitator unavailable, verify succeeds/settle fails, settle succeeds/accounting fails, and retry-after-commit cases;
- multi-process tests for any replay, channel, or subscription store;
- discovery documents validated by upstream parsers;
- packed-project tests so optional mechanism and storage subpaths do not leak Node-only dependencies into portable builds;
- documentation that distinguishes protocol support, SDK integration, facilitator availability, and production storage.

## Confidence and limitations

- **High confidence:** released versions/dates, current protocol feature lists, dependency skew, hard-coded Lucid schemes/networks, missing extensions, process-local MPP state, absent session/subscription/MCP surfaces. These are directly evidenced by official release/spec/source material and local source.
- **Medium-high confidence:** roadmap order and proposed package boundaries. They follow Lucid's documented single-source/domain-ownership architecture and the protocol dependency graph, but implementation estimates require design spikes.
- **Deliberately excluded from “released”:** x402 commits after the 17 July 2.19.0 version commit, even when present on official `main`.
- **Facilitator caveat:** protocol/SDK support does not guarantee that a chosen production facilitator supports a network, asset, scheme, extension, or smart-wallet mode. Lucid must validate `/supported` at startup and document operational availability separately.
